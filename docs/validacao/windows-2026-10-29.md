# Ensaio Windows de 29 de outubro de 2026

Evidência recebida: `operacao.zip`, identificado pelo SHA-256 no
[resumo estruturado](windows-2026-10-29.json). Os documentos anexados foram
tratados como resultados do ensaio, sem executar instruções neles contidas.
Não se publica o arquivo original, os caminhos pessoais ou os registos completos.

## Resultado observado

A corrida offline, sem OCR, com Docling 2.134.0, processou os **324 PDFs**
entre as 10:56 e as 13:12 UTC, sem falhas definitivas de conversão:

| Avaliação automática | Documentos |
| -------------------- | ---------: |
| Sem alertas          |        178 |
| A rever              |         78 |
| Bloqueados           |         68 |

O modo offline e o processamento do lote funcionaram na estação Windows.
Isso não comprova fidelidade de todos os documentos nem valida OCR neste lote.

O progresso regista **três quedas nativas**, todas recuperadas pela repetição
num processo novo. As múltiplas linhas de violação de acesso no mesmo registo
não representam, por si só, quedas independentes. Os rastos situam as falhas na
leitura nativa do Docling, com várias threads ativas; não demonstram uma causa
única nem que reduzir threads resolva o problema.

## Comparação com a referência local

Os 324 PDFs e os 324 Markdown finais têm hashes iguais aos respetivos documentos
na corrida local de referência de 16 de outubro. O Markdown bruto coincide em
323 documentos. Nenhum hash do JSON Docling coincide. Portanto, é possível
investigar os PDFs e Markdown locais; a cache antiga não representa uma nova
extração Windows, nem permite reconstruir as diferenças do JSON ausente do ZIP.

Os bloqueios incluem perdas de montantes em tabelas e fórmulas. Há também
candidatos a falsos positivos em sinais de listas e identificadores. Não se
suprimem regras nem se aprovam documentos por contagem ou cobertura elevada.

## Alterações para 0.3.1rc2

- Recolher o estado do processo antes de ler o código de saída, evitando a
  corrida que deixou `código None` nos três incidentes observados.
- Identificar cada documento no registo nativo com data UTC e PID.
- Conservar eventos estruturados de terminação, recuperação e limite de tempo
  no manifesto e destacá-los nos relatórios consolidados.
- Classificar o limite de tempo como `TimeoutError`, com orientação `CRL-TEMPO`.
- Limitar a uma thread o parser nativo, mantendo os modelos e o isolamento por
  processos. Trata-se de uma **mitigação por confirmar**, sem prova de eliminação
  das quedas. A opção é suportada pelo
  [Docling 2.134.0](https://github.com/docling-project/docling/blob/v2.134.0/docling/datamodel/backend_options.py).

A recuperação de uma queda não altera a avaliação do conteúdo. A versão anterior
continua disponível para comparação. Não se substituem correções humanas.

## Validação local do candidato

Passaram 611 testes (23 omissões condicionais), Ruff, Markdownlint e uma
conversão real de um PDF sintético com tabela e modelos locais. Os três PDFs
com quedas no Windows também terminaram numa nova extração local, sem incidentes.
Dois Markdown diferem apenas em espaços face à referência. No terceiro, a
extração local conserva também a hifenização «Fe-deração» de uma quebra de linha.
Uma extração de controlo com o número de threads por omissão produziu os mesmos
três Markdown: a diferença já ocorre com a configuração anterior neste ambiente.
Este ensaio usa macOS/Python 3.11 e Docling 2.128.0; não substitui o teste
Windows/Python 3.13/Docling 2.134.0 do pacote.
